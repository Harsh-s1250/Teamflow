# AI-Assisted Development

TeamFlow's initial implementation was generated by Claude (Anthropic)
working from a detailed master specification supplied by the developer
(reproduced in spirit throughout this repository's documentation). This
document records how AI was used, what was reviewed, and what a human
developer should still verify before treating this as production-ready.

## How AI was used

For each major area, the workflow was: read the requirement in the
master prompt → design the smallest solution that satisfies it →
implement it directly in the target files → cross-check it against the
adjacent requirements (e.g. does this business rule also need a database
constraint?) → write a test that exercises it.

| Area | Prompt / problem | AI approach | Notes / what to review |
|---|---|---|---|
| Domain model | "5 relational entities with FKs, unique constraints, referential integrity" | JPA entities + a single Flyway migration (`V1__init_schema.sql`) with explicit constraints mirroring the entity annotations | Review that `ddl-auto: validate` doesn't drift from the migration as the schema evolves — always add a new migration, never edit `V1` after it has run anywhere |
| Dependency cycle detection | "Circular dependencies must be rejected" | Breadth-first search over the dependency graph before inserting a new edge (`TaskService.createsCycle`) | O(V+E) per insert; fine at this project's scale. A large, deeply-chained project could reconsider this if dependency graphs become huge |
| Authorization | "Never trust client-supplied userId/role" | All identity reads go through `CurrentUser`, sourced from the validated JWT via Spring Security's context | Review `requireWriteAccess`/`requireManagerOfProject` carefully if new endpoints are added — this is the most security-sensitive code in the app |
| Status transitions | "Invalid state transitions are rejected" | Explicit whitelist map (`ALLOWED_TRANSITIONS`) rather than scattered if/else | Deliberately kept boring/explicit per the project's "don't over-engineer" instruction |
| Frontend | "Medium complexity, no default Vite/React content" | Hand-written CSS design system (CSS variables, no UI framework), React Router pages, Axios client reading `VITE_API_BASE_URL` | The frontend was installed and built (`npm install && npm run build`) in the generating environment and completed with no errors |
| Tests | "Meaningful tests including failure scenarios" | Mockito unit tests for `TaskService`/`ProjectService` business rules; MockMvc integration tests over H2 for auth, authorization, and end-to-end rejection of invalid dates / duplicate membership / incomplete dependencies / circular dependencies | Backend tests were written and reviewed but **could not be executed** in the generating sandbox — no Maven Central network access. Run `mvn test` yourself before relying on them |

## Developer responsibility

The generating environment could not run `mvn compile`/`mvn test`
(network restrictions — see `docs/deployment.md`, final section), so no
claim is made that the backend has been executed successfully. This is
stated explicitly rather than silently assumed, per the project's own
instruction not to claim verification that didn't happen. Before this
code is used for anything beyond review:

1. Run `mvn test` in `backend/` and resolve any compile or test failures.
2. Run the demonstration scenario in the root README end-to-end against
   a real PostgreSQL instance.
3. Review the authorization logic in `ProjectService` and `TaskService`
   line by line — this is the highest-stakes code in the application and
   deserves a human security review regardless of how it was produced.
4. Treat `V2__seed_demo_data.sql` as demo-only; do not ship it to a real
   production database.

## What AI did not decide unilaterally

Scope boundaries (no Kafka/Redis/Kubernetes/microservices, medium-complexity
UI, task-count-based MVP progress formula, etc.) came directly from the
master specification, not from an independent AI judgment call about what
"looks impressive." Where the spec was silent on a minor detail (e.g. the
exact allowed status-transition graph, or that a project manager is
auto-added as a member of their own project), the simplest
architecture-consistent choice was made and is documented in
`DEVELOPMENT_DECISIONS.md`.
